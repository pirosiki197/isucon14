# 進め方

## 1 手ずつ測る

複数の変更をまとめて入れると、何が効いたか分からなくなる。
悪化したときに切り分けもできない。**変更 → ベンチ → digest/alp 確認**を 1 セットにする。

ベンチはばらつく。今回 同一条件で 8203 / 7412 / 7561 と ±10% 程度振れた。
**数％の差を改善と呼ばない。** 効いた変更は倍近く動くので、迷うなら効いていない。

## 推測を実測で潰す

「たぶんこれが原因」で改修に入ると、外れたときに大きな手戻りになる。
今回、外した推測が 3 つあった。

| 推測 | 実際 |
|---|---|
| 窓関数は `PARTITION BY` の順序がインデックスと一致するのでソートが省ける | `Using filesort` が残り、1.93s → 1.75s とほぼ無変化 |
| `UPDATE chairs` が遅いのは認証の読み取りと競合しているから | インデックスを足しても 11.6ms → 11.7ms。原因は fsync だった |
| `COMPLETED` があれば `ARRIVED`/`CARRYING` もあるはず | 実データに例外が 2 件。条件を単純化していたら結果が変わっていた |

いずれも**着手前に 1 コマンド打てば分かった**。`EXPLAIN`、`SHOW GLOBAL STATUS` の差分、
`SELECT COUNT(*)` での件数照合。改修より測る方が圧倒的に安い。

## 結果が変わらないことを確認してから置き換える

クエリの書き換えや非正規化では、**新旧の結果を突き合わせてから**デプロイする。
ベンチを落としてから原因を探すより速い。

```sql
-- 全件について新旧の結果が一致するか数える
SELECT SUM(cnt_new <> cnt_old) AS mismatch FROM ( ... ) t;
```

今回は「529 台すべてで件数・平均が一致」「500 台すべてで距離・座標・時刻が一致」を
確認してから進めた。前述の `ARRIVED` の例外はこの過程で見つかった。

## 環境の壊れを疑う

スコアが出ない原因がアプリとは限らない。今回あったもの:

- **nginx の TLS 証明書が失効**していて、`curl -s` で内部 API を叩くマッチング処理が
  毎回失敗していた。`-s` なのでログにも出ず、ベンチが「マッチングされない」で落ちていた
- ベンチの起動オプションで**決済モックの URL がアプリサーバ自身を指していた**ため、
  決済が全て connection refused になっていた

「アプリを直しても直らない」ときは、**周辺の疎通を手で確認する**。
`curl` の終了コード、`ss -tlnp` で誰が何を LISTEN しているか、証明書の有効期限。

## ベンチマーカー側が律速していないか

ベンチが小さいインスタンスだと、負荷をかけ切れずスコアが頭打ちになる。
**アプリ側とベンチ側の両方で CPU を測れば一発で分かる。**

今回は c5a.large (2 vCPU) で、負荷走行中も **idle 82%** だった（アプリ側は idle 5.6%）。
律速はアプリ側と確認できたので、以降は安心してアプリを削れた。

## 計測基盤のコスト

分散トレーシング (OpenTelemetry → Grafana Cloud) は入れたが、
**digest と alp で足りている間は出番が無い**ので途中で export を止めた。

送信量は事前に見積もる。今回の実測:

- slow query log を Loki に送ると **1 リクエスト 32KB / ベンチ 1 回 54MB**。
  Free 枠 50GB/月 の 6 割をこれだけで使う計算になり、転送は止めた
- トレースは 10% サンプリングで **ベンチ 1 回 2 万スパン**。こちらは余裕があった

トレースには SQL が `db.query.text` として乗るので、**slow log を別途送るのは情報が重複する**。
生ログを転送するより、サーバ上で `pt-query-digest` に食わせる方が速くて安い。

## 計装を切れるようにしておく

計測エージェント自体が CPU を食う。2 vCPU では無視できないので、
**環境変数ひとつで無効化できる**ようにしておくと、最終計測前に落とせる。

```bash
OTEL_SDK_DISABLED=true          # アプリの計装
SET GLOBAL slow_query_log = OFF # slow log
```

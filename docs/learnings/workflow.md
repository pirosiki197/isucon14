# 進め方

## 最初に変動幅を測る

**これを最初にやらなかったのが、今回いちばんの反省点。**

同一コードでベンチを 3 回以上回して、スコアの幅を出す。これをやる前に
「A と B のどちらが速いか」を 1 回ずつの走行で比べても、答えは出ない。

今回、同一コードで 7 回回した結果:

```
47871  48439  48812   ← 連続 3 回
56001                 ← 間を空けた 1 回
55251  55487  52234   ← 連続 3 回
```

**幅 17%。しかも塊で偏る。** 実行間隔・I/O バースト・journald をそれぞれ測って
否定したが、原因は特定できなかった。原因が分からなくても、**幅を知っていれば
判断は守れる**。

これを知らずに、次の 2 つの失敗をした。

- ポーリング間隔を 350 / 450 / 600ms で 1 回ずつ比較し「350 が最適」と結論した。
  全部ノイズの中だった。意味があったのは 50ms → 350ms という**大きな傾向だけ**
- ある変更の後にスコアが下がったので自分の変更のせいだと考えて revert した。
  revert 後も下がったままで、変更は無関係だった

### 幅より小さい差をどう扱うか

**スコアを諦めて、直接測れる量に切り替える。**

| 見たいこと | スコア以外の証拠 |
|---|---|
| クエリを減らせたか | digest の Count、`grep -c` でのクエリ実測 |
| インデックスが効いたか | `EXPLAIN` の `type`/`key`、`Rows examined` |
| リクエストを減らせたか | alp の Count |
| CPU が空いたか | `CPUUsageNSec` の差分 |

今回、認証キャッシュは「スコア +8%（判定不能）」だったが、
「`users` の認証クエリが 21,276 回 → 約 300 回」は**確実に測れた**。
やる仕事が厳密に減っているなら、スコアで見えなくても入れる方が正しい。

逆に、**幅を超える差が出たなら素直に信じてよい**。椅子の認証キャッシュは
3 回すべてが前回の最高値を上回ったので、変動では説明できない。

## 1 手ずつ測る

複数の変更をまとめて入れると、何が効いたか分からなくなる。
悪化したときに切り分けもできない。**変更 → ベンチ → digest/alp 確認**を 1 セットにする。

1 手あたり「3 回計測」が前提になると 1 サイクル 8 分かかる。
**大きく効く手から順にやる**理由がここにもある。小さい手は測れない。

## 推測を実測で潰す

「たぶんこれが原因」で改修に入ると、外れたときに大きな手戻りになる。
今回、外した推測が 3 つあった。

| 推測 | 実際 |
|---|---|
| 窓関数は `PARTITION BY` の順序がインデックスと一致するのでソートが省ける | `Using filesort` が残り、1.93s → 1.75s とほぼ無変化 |
| `UPDATE chairs` が遅いのは認証の読み取りと競合しているから | インデックスを足しても 11.6ms → 11.7ms。原因は fsync だった |
| `COMPLETED` があれば `ARRIVED`/`CARRYING` もあるはず | 実データに例外が 2 件。条件を単純化していたら結果が変わっていた |
| slow log の 54MB/走行が mysql の CPU を膨らませている | 計装を全部切っても 125.1s → 123.6s。1.2% しか変わらなかった |
| スコアが下がったのは直前の自分の変更のせい | revert しても下がったまま。ベンチの変動だった |

いずれも**着手前に 1 コマンド打てば分かった**。`EXPLAIN`、`SHOW GLOBAL STATUS` の差分、
`SELECT COUNT(*)` での件数照合。改修より測る方が圧倒的に安い。

## ベンチマーカーが検証する値は、どの時点を数えているのか

ベンチが「サーバの返した値が想定と違う」と言うとき、**値そのものではなく
「いつの時点の値か」がずれている**ことがある。今回これで 4 回外した。

椅子の累計乗車回数が常に `+1` ずれる、という症状に対して:

| 試したこと | 結果 |
|---|---|
| 通知中のライドを集計から除外 | `-1` に反転 |
| 「通知済み」条件を追加（統計を読んだ後に印を刻む） | `-1` |
| 同条件 + 印を先に刻む | **0 件** |
| カウンタ化して通知時に加算 | `-1` が 132 件 |
| カウンタ化して評価時に加算 | `+1` が 132 件 |
| カウンタ化して印と加算を 1 文で更新 | **0 件** |

**推測を止めて、真値を再構成したことで解けた。**
ベンチのログには発生時刻・対象 ID・got/want が出る。一方 DB には
`created_at` / `app_sent_at` / `chair_sent_at` が残っている。
そこで「その時刻に各候補が何件だったか」を SQL で計算し、`want` と照合した。

```sql
-- エラーの (時刻, ID, got, want) を一時表に入れ、候補ごとに件数を数える
SELECT COUNT(*) AS samples,
  SUM(evaluated    = want) AS evaluated_eq_want,
  SUM(app_notified = want) AS app_notified_eq_want,
  SUM(chair_notified = want) AS chair_notified_eq_want
FROM (SELECT e.*,
       (SELECT COUNT(*) ... AND s.created_at    <= e.at) AS evaluated,
       (SELECT COUNT(*) ... AND s.app_sent_at   <= e.at) AS app_notified,
       (SELECT COUNT(*) ... AND s.chair_sent_at <= e.at) AS chair_notified
      FROM _e e) x;
```

結果は `app_notified` が 170/170 で一致、他は 0/170。**境界が一発で確定した。**
さらに「エラーが出た通知は、完了したライド自身ではなく同じ椅子の古いライドを
見ている別ユーザーのポーリングだった」ことも同じ方法で分かり、
原因が**2 つの更新の間の隙間**だと特定できた。

やり方は問題に依存しない。**ログの時刻 × DB のタイムスタンプで過去を再構成する。**

## 結果が変わらないことを確認してから置き換える

クエリの書き換えや非正規化では、**新旧の結果を突き合わせてから**デプロイする。
ベンチを落としてから原因を探すより速い。

```sql
-- 全件について新旧の結果が一致するか数える
SELECT SUM(cnt_new <> cnt_old) AS mismatch FROM ( ... ) t;
```

今回は「529 台すべてで件数・平均が一致」「500 台すべてで距離・座標・時刻が一致」を
確認してから進めた。前述の `ARRIVED` の例外はこの過程で見つかった。

## 環境の壊れを疑う

スコアが出ない原因がアプリとは限らない。今回あったもの:

- **nginx の TLS 証明書が失効**していて、`curl -s` で内部 API を叩くマッチング処理が
  毎回失敗していた。`-s` なのでログにも出ず、ベンチが「マッチングされない」で落ちていた
- ベンチの起動オプションで**決済モックの URL がアプリサーバ自身を指していた**ため、
  決済が全て connection refused になっていた

「アプリを直しても直らない」ときは、**周辺の疎通を手で確認する**。
`curl` の終了コード、`ss -tlnp` で誰が何を LISTEN しているか、証明書の有効期限。

## ベンチマーカー側が律速していないか

ベンチが小さいインスタンスだと、負荷をかけ切れずスコアが頭打ちになる。
**アプリ側とベンチ側の両方で CPU を測れば一発で分かる。**

今回は c5a.large (2 vCPU) で、負荷走行中も **idle 82%** だった（アプリ側は idle 5.6%）。
律速はアプリ側と確認できたので、以降は安心してアプリを削れた。

## 計測基盤のコスト

分散トレーシング (OpenTelemetry → Grafana Cloud) は入れたが、
**digest と alp で足りている間は出番が無い**ので途中で export を止めた。

送信量は事前に見積もる。今回の実測:

- slow query log を Loki に送ると **1 リクエスト 32KB / ベンチ 1 回 54MB**。
  Free 枠 50GB/月 の 6 割をこれだけで使う計算になり、転送は止めた
- トレースは 10% サンプリングで **ベンチ 1 回 2 万スパン**。こちらは余裕があった

トレースには SQL が `db.query.text` として乗るので、**slow log を別途送るのは情報が重複する**。
生ログを転送するより、サーバ上で `pt-query-digest` に食わせる方が速くて安い。

## 計装を切れるようにしておく

計測エージェント自体が CPU を食う。2 vCPU では無視できないので、
**環境変数ひとつで無効化できる**ようにしておくと、最終計測前に落とせる。

```bash
OTEL_SDK_DISABLED=true          # アプリの計装
SET GLOBAL slow_query_log = OFF # slow log
```

# 複数台構成

1 台で CPU を使い切った状態（idle 1.4%）から DB を別サーバに出しただけで
**約 60,800 → 100,632（+66%）**。今回の単発の変更としては最大だった。

**リソースを増やす手は、コードを削る手より効く。** 残っている効率化が数％しか
見込めない局面なら、先に構成を疑う。

## どちらを移すか

**DB を移すのが簡単。** アプリを移すと言語のツールチェインが必要になるが、
DB 側に必要なのは MySQL の設定だけ。今回、新サーバには古い Go しか入っておらず
`go.mod` の要求バージョンを満たせなかったが、DB 専用にしたので問題にならなかった。

CPU の配分を見て決める。今回は mysql 61s / アプリ 35s / nginx 18s だったので、
mysql を出せばアプリ側に 2 倍以上の余裕ができる計算になる。

## 手順

```bash
# 1. DB 側: 待ち受けを開く
#    /etc/mysql/mysql.conf.d/mysqld.cnf
bind-address = 0.0.0.0

# 2. DB 側: アプリサーバからの接続を許可
CREATE USER 'isucon'@'<app の内部IP>' IDENTIFIED BY 'isucon';
GRANT ALL PRIVILEGES ON *.* TO 'isucon'@'<app の内部IP>';

# 3. DB 側: チューニング設定を複製する（後述。忘れると過去の改善が消える）
scp z-isucon-tuning.cnf z-isucon-slow.cnf db:/etc/mysql/mysql.conf.d/

# 4. アプリ側: 接続先を変える
ISUCON_DB_HOST="<db の内部IP>"

# 5. アプリ側: ローカルの MySQL を止める
sudo systemctl stop mysql && sudo systemctl disable mysql
```

### チューニング設定の複製を忘れない

**新サーバの MySQL は素の設定。** fsync 設定を複製しないと、
過去に稼いだ改善（今回 fsync 3万回 → 939回）がまるごと失われる。
移行後に必ず確認する。

```sql
SELECT @@hostname, @@innodb_flush_log_at_trx_commit, @@slow_query_log;
```

### init.sh は書き換え不要なことが多い

初期化スクリプトが `--host "$ISUCON_DB_HOST"` の形で書かれていれば、
**アプリサーバ上で実行したままリモート DB を初期化できる**。
SQL ファイルを DB サーバへコピーする必要もない。

`POST /api/initialize` が exec するスクリプトなので、まずここを読んで
ホストが環境変数から来ているかを確認する。ローカルの `mysql` に決め打ちなら書き換える。

## 詰まったところ

### Requires=mysql.service が MySQL を引き戻す

アプリの unit に `Requires=mysql.service` があると、**`systemctl restart` のたびに
止めたはずの MySQL が起動する**。「停止したのに active」という現象になる。
DB がリモートになったら `After=` と `Requires=` の両方を消す。

### Connection refused とタイムアウトを区別する

疎通確認の結果で切り分けが変わる。

```bash
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/<db-ip>/3306'
```

- **Connection refused** → パケットは届いている。**待ち受け設定（bind-address）の問題**
- **タイムアウト** → セキュリティグループ / ファイアウォールの問題

今回 refused だったので、AWS のセキュリティグループは触らずに済むと即断できた。

## 分割の代償

**DB アクセスがループバックから実ネットワークになり、`sy` が上がる。**
今回 31% → 40% で、増えた約 9 ポイントがその分。

つまり**1 リクエストあたりのクエリ本数が多い実装ほど、分割で損をする**。
今回は事前に N+1 と認証クエリを潰してあったので差し引きで大きく勝ったが、
クエリを削っていなければ往復の増加で相殺されていた可能性がある。

**分割は「クエリを削る」の代わりではなく、その後にやると効きが良い。**

## ボトルネックは移動する

分割後の CPU:

| サーバ | idle |
|---|---|
| アプリ | 14.2% |
| DB | 20.2% |
| ベンチ | 47.6% |

この状態でアプリ側を改善（nginx を unix socket 化）すると、
**アプリの idle は 14.2% → 23.1% に増えたのにスコアは動かなかった。**
DB の idle が 20.2% → 16.5% になり、律速がそちらへ移っていた。

**1 段階ごとに「どのサーバの idle が最小か」を測り直す。**
それを見ずに同じ層を改善し続けても数字は動かない。

## ベンチマーカーが律速していないか

分割で 1.6 倍のスループットになると、ベンチ側の余裕も減る。

```
61k  のとき: ベンチ idle 65.5%
100k のとき: ベンチ idle 49.3%
```

この傾きだと 15 万前後でベンチが飽和する。**上限が見えたら、そこから先は
アプリを速くしても数字にならない**ので、計測の前提として把握しておく。

## 今回の推移

初期実装から 57 倍。**1 手ごとにベンチを回して効果を確認した**のが重要で、
まとめて変更すると何が効いたか分からなくなる。

| # | 変更 | スコア | 備考 |
|---|---|---|---|
| 0 | 初期実装 | 1075 | |
| 1 | `ride_statuses(ride_id, created_at)` | 2168 | クエリ単価 21.8ms → 0.3ms |
| 2 | `chair_locations(chair_id, created_at)` | 2819 | |
| 3 | 窓関数サブクエリに絞り込みを押し込む | 4218 | SQL 1 行。1.75s → 63ms |
| 4 | ポーリング間隔 30ms → 100ms | 5761 | |
| 5 | 座標と累積距離を `chairs` に非正規化 | 6343 | |
| 6 | `chairs(access_token)` | 8203 | 認証が全リクエストに乗っていた |
| 7 | fsync 設定 (`flush_log_at_trx_commit` 等) | 8707 | fsync 3万回 → 939回 |
| 8 | `rides` と `coupons` にインデックス | 9213 | digest の 59.5% が 16% に |
| 9 | マッチング起動間隔 0.5s → 0.1s | 14887 | env.sh の 1 行 |
| 10 | マッチングを距離・速度考慮の一括割り当てに | 23820 | `ORDER BY RAND()` を廃止 |
| 11 | nearby-chairs を 1 クエリに | 32678 | 574+N 本 → 1 本 |
| 12 | `rides.latest_status` を非正規化 | 41483 | 同時実行度 5.4x → 0.9x |
| 13 | 椅子統計をカウンタ化 | 43889 | 検証エラーも解消 |
| 14 | ポーリング間隔 350ms | 約 55k | 100ms から +28% |
| 15 | 認証をメモリキャッシュ | 約 60.8k | 全クエリの 24% が消滅 |

**局面が 3 回変わった。** 序盤（1〜8）はインデックスと設定で単価を下げる勝負。
中盤（9〜13）は N+1 と集計を潰してクエリ本数を減らす勝負。
終盤（14〜15）は**クエリ 1 本の単価がもう下がらなくなり、リクエストあたりの
固定費とリクエスト数の勝負**になった。使う道具も digest → alp → CPU 配分と移っていく。

## 最初の 30 分でやること

1. **同一コードでベンチを 3 回回して、変動幅を知る**（後述。これを最初にやらないと後で判断を誤る）
2. `pt-query-digest` と `alp` を使えるようにする（ログ設定込みで 10 分）
3. 主キー以外のインデックスが無いテーブルを探す → `WHERE` 句と突き合わせて貼る
4. MySQL の fsync 設定を落とす
5. Go の `SetMaxIdleConns` を設定する

2〜5 は**ほぼ何も考えずに効く**。考えるのはその後でいい。

そして 1 が抜けると、以降の全ての判断が疑わしくなる。今回**ベンチの変動幅は 17%** あり、
それを知らずに 1 回ずつの比較で「最適値」を決めていた時間があった（[workflow.md](workflow.md)）。

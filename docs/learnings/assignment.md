# 定期起動のバッチ処理と割当問題

「一定間隔で叩かれて、待っている仕事を処理する」形の処理は ISUCON によく出る。
マッチング、キュー消化、集計更新など。ここに**隠れたスループット上限**がある。

## 1 回 1 件は上限を作る

初期実装はこうなっていた。

```go
// 0.5 秒ごとに呼ばれ、1 回につき 1 件だけ処理する
SELECT * FROM rides WHERE chair_id IS NULL ORDER BY created_at LIMIT 1
for range 10 {
    SELECT ... ORDER BY RAND() LIMIT 1   // 空きか未確認のまま引く
    SELECT COUNT(*) = 0 FROM (...)       // 引いたものが空きか確認
}
```

**上限が 2 件/秒に固定される。** しかもランダムに引いたものが埋まっていれば
最大 10 回外して、その周期は 1 件も処理せずに終わる。

DB を 28% 速くしてもスコアが動かなかったのに、**起動間隔を 0.5s → 0.1s に
変えるだけで +62%** 伸びた。**律速がクエリ単価ではなく処理の供給量だった。**

順番として、**まず間隔を詰めて律速かどうかを確認する**のが安い。
設定 1 行で済み、外れても損がない。効いたらアルゴリズムを書き換える根拠になる。

## 割当問題には名前がある

待っている仕事の集合と、空いている処理主体の集合を、コスト最小で対応付ける。
これは**割当問題 (assignment problem / linear sum assignment)** で、
配車サービス文脈では **order dispatch / batched matching** と呼ばれる。

| 手法 | 計算量 | 最適性 | 実装量 |
|---|---|---|---|
| 貪欲（辺をコスト順にソートして順に確定） | O(nm log nm) | 近似 | 20 行 |
| ハンガリアン法 (Kuhn-Munkres) | O(n³) | 最適 | 100 行 |
| 最小費用流 | 実用上は高速 | 最適 | ライブラリ次第 |

**ISUCON の規模なら貪欲で十分。** 待ち仕事が数十・処理主体が数百なら辺は数千本で、
貪欲なら 1ms 未満。ハンガリアン法でも n=100 なら数 ms なので、
**どちらでも計算時間は問題にならない**。だから先に実装が軽い方を入れて測る。

そして重要なのは、**最適に解いてもコスト関数が雑なら意味がない**こと。
誤差の主因はアルゴリズムよりコスト関数側にある。

```go
// 全ペアをコスト順に見て貪欲に確定させる
pairs := make([]pair, 0, len(jobs)*len(workers))
for i := range jobs {
    for j := range workers {
        pairs = append(pairs, pair{i, j, cost(jobs[i], workers[j])})
    }
}
sort.Slice(pairs, func(a, b int) bool { return pairs[a].cost < pairs[b].cost })
for _, p := range pairs {
    if jobTaken[p.job] || workerTaken[p.worker] { continue }
    // 確定
}
```

## コスト関数の作り方

**距離ではなく時間で組む。** 今回、処理主体（椅子）にはモデルごとに `speed` があった。
距離だけで最適化すると、遅い個体に長い仕事を割り当ててしまい、
ベンチの「実移動時間の不満」が下がらない。

```
コスト = (迎えに行く距離 + 運ぶ距離) / 速度
```

**ベンチの評価軸とコスト関数を対応させる。** 今回ベンチは 3 種類の不満を出していた。

| ベンチの不満 | コストのどの項 |
|---|---|
| マッチされるまでの時間 | 供給量（間隔・1 回の処理件数） |
| 迎えに来るまでの時間 | 迎えに行く距離 / 速度 |
| 実移動時間 | 運ぶ距離 / 速度 |

書き換え後、迎車の不満は 84.7% → 34.2% に落ちた。
一方で実移動時間の不満は下がらず、調べると**速い個体が全体の 27% しかいない**
という供給制約だった。**下がらない不満は、まず母数を数える。**

貪欲法の弱点もここに出る。**一番安いペアから確定するので、
近くにいた速い個体が短い仕事に消費される。** 希少な資源を長い仕事に回したいなら、
ハンガリアン法に寄せるか、コストに重みを入れる必要がある。

## 飢餓を防ぐ

コストだけで選ぶと、辺境で発生した仕事が永久に処理されない。
今回それは**クリティカルエラーで即 fail** だったので、点数以前の問題だった。

定石は待ち時間の項を入れること。

```
コスト = 所要時間 - α × 待ち時間
```

これは「どの処理主体を選ぶか」は変えず、**貪欲の確定順だけを変える**ので副作用が小さい。
単純に「一定秒数以上待っている仕事を先に確定させる」でも足りる。

## バッチ窓のトレードオフ

溜めるほど良い組み合わせが選べるが、溜めた時間はそのまま待ち時間になる。
配車の論文でも中心的な論点で、**実測で決めるしかない**。

まずは「起動間隔ごとに、その時点の待ち仕事すべて × 空き主体すべて」で始めるのが素直。

## 空き判定を集合で取れる形にする

1 件ずつ処理する実装は「1 個引いて空きか確認」を繰り返せるが、
一括処理では**空いている主体の集合を 1 クエリで取る**必要がある。

元の判定が集計（履歴テーブルを数える）なら、そのままでは一括にできない。
フラグやカウンタに非正規化することになるので、
[go-webapp.md](go-webapp.md#カウンタ化はクエリと違って自己修復しない) に注意する。

移行時は**元の判定式と新しいフラグが全件で一致することを SQL で確認してから**進める
（[workflow.md](workflow.md#結果が変わらないことを確認してから置き換える)）。

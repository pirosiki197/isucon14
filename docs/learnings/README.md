## 最初の 30 分でやること

1. `pt-query-digest` と `alp` を使えるようにする（ログ設定込みで 10 分）
2. 主キー以外のインデックスが無いテーブルを探す → `WHERE` 句と突き合わせて貼る
3. MySQL の fsync 設定を落とす
4. Go の `SetMaxIdleConns` と `InterpolateParams` を設定する
5. `signal.NotifyContext` に `SIGQUIT` を足す（1 行。放置すると後で高くつく）
6. 定期起動のバッチ処理があれば、起動間隔を詰めて律速かどうかを見る

いずれも**ほぼ何も考えずに効く**。考えるのはその後でいい。

## 局面は変わる

初期実装から 57 倍まで伸ばした過程で、**効く手の種類が 4 回変わった**。
使う道具も digest → alp → CPU 配分と移っていく。

|---|---|---|---|

| 16 | **DB を別サーバへ分離** | **約 99.4k** | 単発では最大の +66% |
| 17 | nginx を unix socket + fd 上限 | 約 99.2k | CPU は空いたがスコアは横ばい |

- **序盤（1〜8）はインデックスと設定で単価を下げる勝負。** digest の上位から機械的に潰す
- **中盤（9〜13）は N+1 と集計を潰してクエリ本数を減らす勝負。** digest では見えないので alp を併用する
- **終盤（14〜15）はクエリ 1 本の単価がもう下がらず、リクエストあたりの固定費とリクエスト数の勝負**
- **最後（16〜17）は台数を増やして、律速がどの層にあるかを追いかける勝負**

17 が横ばいだったことが象徴的で、**アプリサーバの idle を 14% → 23% に増やしても、
DB が 16.5% で詰まっていればスコアは動かない**。改善した層と律速の層は別々に見る。
